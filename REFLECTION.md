# Reflection

I drew the lines between the three tools by asking one question about each: does it **read** something, **change** something, or **decide** something? `get_weather_forecast` only reads. It resolves a city and returns a typed forecast, and it can be called a hundred times without side effects. `save_outing` only changes state. It validates and appends one outing, and it knows nothing about weather. The hardest boundary was the "decision" part: choosing the best day for an activity. My first idea was a `save_best_day` action, but describing it needed an "and" ("check the weather *and* save"), which is exactly the warning sign from class. So that logic went into the orchestration tool, `plan_outing`, which calls the same core functions as the other two tools and adds only the scoring rules. The same thinking decided the resources: the saved outings and the activity rules are pure lookups, so they are exposed as `@mcp.resource`s instead of extra tools. One place where I accepted a small compromise is the Data tool: it geocodes the city *and* fetches the forecast. I kept it as one tool because, from the agent's point of view, "get the weather for Byblos" is a single intent, and splitting it would force the model to pass coordinates around. Every tool fails loudly with a specific message (unknown city, days outside 1–7, weather service down, past or badly formatted date, duplicate outing, unknown activity), and the tests check each of these.

Three tools felt right for this use case. The agent's routing stayed simple: "what's the weather" maps to the Data tool, "save this" to the Action tool, and "find me the best day" to the Orchestration tool. A fourth tool would have made the choice harder without adding a new kind of capability. The trade-off is that the orchestration tool is less flexible than letting the LLM chain the steps itself. It always saves the single best day, and its activity rules are fixed. As next steps, I would:

1. Add a `delete_outing` action, so plans can be cancelled.
2. Let users adjust the activity rules (for example "I don't mind light rain").
3. Cache forecasts for a few minutes, to stay within the free API's limits.
4. Serve the MCP server over HTTP instead of stdio, so several clients (for example Claude Desktop and this agent) could share the same saved outings.
